Akana to Apigee X Migration Strategy

Migrate by business-use product, not by API inventory.

01 / 11

Executive answer

Use Apigee X as the new governed API operating model, and move one business usage grouping at a time through a repeatable migration factory. Keep Akana live only as a controlled coexistence path through the external load balancer.

  • 1Define every migration unit as an Apigee Product aligned to a use case, consumer group, SLA, identity pattern, and lifecycle owner.
  • 2Stand up core platform controls once: Ping integration, cert patterns, CI/CD, policy templates, product taxonomy, and onboarding gates.
  • 3Run each product through discover, design, build, prove, onboard, cutover, and retire, with clear exit criteria before the next product starts.

Situation

Akana runs critical APIs.

The current gateway estate supports business capabilities, but the implementation has grown around delivery pressure rather than deliberate platform design.

Complication

The design debt is structural.

Poor product taxonomy, inconsistent gateway patterns, tight coupling, manual deployments, and weak governance make a bulk migration risky.

Question

How do we migrate without moving the mess?

Move the business capability, consumers, policies, certificates, and onboarding model together, rather than translating individual proxies.

Answer

Use product waves.

Each Apigee Product becomes a governed migration unit with explicit consumers, identity model, SLAs, traffic path, ownership, and retirement criteria.

Decision required: endorse product-led migration as the default unit of change MECE lens: platform, product, consumer, operations, risk

Challenges, Pitfalls, and Prevention

Most migration failures come from unmanaged coupling, not Apigee technology.

Issue one might face
Prevention recommendation
Bad Akana taxonomy gets recreated. Teams lift and shift proxy groupings.
Require product design approval based on business use case, consumer segment, SLA, owner, and lifecycle before any build starts.
Consumers are discovered late. Hidden apps depend on legacy routes or certificates.
Use Akana logs, LB logs, cert inventory, app registry, and support data to build a consumer evidence pack per product.

Create a Ping-to-Apigee auth contract: issuers, audiences, scopes, claims, token handling, and rejected-token behavior.
Manual deployment habits continue. Apigee becomes another manually changed runtime.
Make CI/CD the only standard path. Exceptions require time-bound architecture approval and post-change reconciliation.
Coexistence becomes permanent. Akana routes stay open after cutover.
Define decommission gates up front: traffic zero, consumers moved, certs revoked, route removed, config archived, ownership closed.

Recommended governance cadence

Weekly product wave review: readiness, open decisions, risk burn-down, consumer onboarding, and route retirement.

Fortnightly architecture board: exceptions, new patterns, policy catalog, Ping model, cert model, and cross-product dependencies.

Monthly executive checkpoint: migrated business capability, Akana dependency retired, operational risk reduced, and next product approved.

Final rule: every migration must leave the platform simpler than it found it.

Last recommendation: protect product taxonomy, automation, identity, and retirement discipline from day one Pitfalls playbook

Concrete Solution Blueprint

Build a reusable Apigee X product platform, then onboard each migrated product into it.

09 / 11
1. Platform foundation

Apigee X org, envs, and routing

Create non-prod and prod environments, environment groups, hostnames, shared VPC connectivity, target routing, external load balancer rules, firewall allowlists, and DNS entries. Keep Akana and Apigee behind the same traffic steering layer during migration.

2. Standard proxy template

One build pattern per product

Use a base proxy structure: PreFlow authentication, threat protection, quota and spike arrest, request normalization, target selection, response mapping, fault rules, structured logging, and analytics dimensions. Ban hand-built policy drift unless approved.

3. Identity solution

Ping-to-Apigee contract

Define issuer, audience, JWKS or introspection, token lifetime, scope naming, claims required for routing and authorization, rejected-token error format, and app registration ownership. Implement this as shared flow plus product-specific scope checks.

4. Certificate solution

Truststore and rotation model

Create keystore and truststore naming standards, mTLS decision rules, cert owner records, rotation windows, expiry alerts, chain validation tests, and decommission steps for Akana-era certificates after each product cutover.

5. CI/CD solution

Config-driven deployment

Use Git as source of truth: proxy bundles, shared flows, env config, product definitions, developer app metadata, tests, and release manifests. Pipeline stages: lint, policy tests, deploy non-prod, integration tests, approval, deploy prod.

6. Portal solution

Consumer onboarding workflow

For each Apigee Product publish docs, usage terms, subscription approvals, app credentials, quota visibility, support contact, change notices, and migration dates. Treat consumer onboarding as part of the build, not post-deployment admin.

Reference implementation pattern

Consumer -> External LB -> Apigee X -> backend for migrated products.

Consumer -> External LB -> Akana -> backend only for products not yet migrated.

Route by product hostname or path and preserve a rollback rule for the agreed stabilization window.

Multi-Consumer API Strategy

Use one canonical proxy for the capability, and multiple API Products for consumer-specific control.

10 / 11

Target model for shared business APIs

Canonical proxy Example: `customer-profile-v1`. Owns backend contract, routing, common security, logging, error mapping, and versioning.
API Products `Customer Profile - Internal`, `Customer Profile - Partner`, `Customer Profile - Digital`. Each product controls access, scopes, quota, SLA, and docs.
Consumer apps Separate developer app, Ping client, credential, approval workflow, owner, cert dependency, and migration date for each consuming application.
Migration waves Move consumers by risk and readiness. Start with low-risk real traffic, then medium-risk, then critical/high-volume consumers.
Design rule: API Products differentiate consumers; proxies represent technical implementation boundaries.

Discover consumers first

Cross-check Akana logs, LB logs, Ping clients, cert inventory, app registry, support tickets, and analytics before any cutover.

Preserve contract

Initially keep URL, payload, status code, headers, auth behavior, error format, and timeout expectations equivalent to Akana.

Onboard in parallel

Pre-create Apigee apps, API Product subscriptions, Ping clients, scopes, credentials, certs, and portal instructions before routing changes.

Cut over by consumer

Route by hostname, path, header, or temporary Apigee hostname. Keep rollback to Akana explicit and time-boxed for each wave.

Minimal disruption: migrate consumers at their own risk pace while keeping the Apigee implementation clean and reusable Consumer wave strategy

Build tasks

Create Apigee proxies, shared-flow attachments, API Product, developer apps, target server config, KVM/config entries, quota settings, custom attributes, fault rules, logging schema, and analytics dimensions.

Done when: deployment is repeatable from Git to non-prod and prod.

Security tasks

Validate Ping issuer, audience, scopes, token expiry, JWKS rotation or introspection, mTLS chain, certificate expiry, PII logging rules, threat protection limits, and rejected-token response format.

Done when: security tests include positive and negative cases.

Cutover tasks

Freeze Akana changes, publish consumer notice, preload credentials, set LB route to Apigee, monitor latency/error/quota/auth metrics, keep rollback route ready, and declare stabilization end time.

Done when: traffic runs through Apigee within agreed SLOs.

Retirement tasks

Remove Akana product route, disable unused apps, revoke legacy certs, archive Akana policy export, mark product migrated, close exceptions, and feed lessons back into templates.

Done when: no production path or credential depends on Akana.
Gate to next product: no open critical defects, no unknown consumers, no manual deployment dependency, no indefinite Akana route End of deck
